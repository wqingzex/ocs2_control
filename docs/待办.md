## 1. 夹爪（`GripperController`）

夹爪原来是独立插件 `gripper_controller`（原 `adaptive_gripper_controller`），现在是 `end_effector_controller` 包里的插件 `end_effector_controller/GripperController`（见 `end_effector_controller/README.md`）。走关节空间状态机，所以 HOLD、HOME 和 MOVEJ 插值都和其他实例一致，原来记下的三个差异随之解决：

- 响应 `fsm_command`：HOLD 停在当前位置，HOME 回到初始位置（`home_1`，没写就用 URDF 的 `initial_value`）。
- 激活后默认 HOLD（和其他实例一致），夹爪不再自己冲向初始位置；要执行开合命令，要先把控制器放行到 MOVEJ（`fsm_command` 是全局话题，机械臂切到 MOVEJ 时夹爪跟着切）。
- 速度限制：默认 `movej_interpolation_type: none`，目标直接写给硬件（和原来一致）；要平滑把它改成 `linear` / `tanh` 并设 `movej_duration`。

**行为变化**：不经状态机、直接给夹爪发 `target_command` / `target_percent` 的外部脚本，现在在 HOLD 状态下会被忽略。仓库内的 VR 遥操作和 RViz 的 FSM 面板会发全局 `/fsm_command`，操作员把机械臂切到 MOVEJ 时夹爪跟着切，所以不用改；仓库外的脚本需要先发 `fsm_command`（3 或 4）。

**验证**：用单关节夹爪（`mock_components`，`end_effector_controller/test/gripper_mock/run.sh`）测了开合、百分比、HOLD、解除、重新激活保持位置、HOME，以及力反馈的代码路径（给 mock 一个常数 effort），结果和合并前的独立插件一致。

**还没验证**：真机上的力反馈和 HOLD 的停止效果（mock 没有真实 effort）；`gripper.launch.py` 里的 `changingtek_description` 配置不在本仓库，如果它还在用旧插件类型 `gripper_controller/GripperController`，要改成 `end_effector_controller/GripperController`。

## 2. 遥操作包的命名和拆分

已经定了：`arms_target_manager` 改名为 `teleop_command`（类 `TeleopCommand`，命名空间 `teleop_command`，节点 `teleop_command_node`，启动参数 `enable_teleop_command`）。遥操作包的命名规则是按输入设备命名（`xr_`、`joystick_`、`keyboard_`）；`manual_teleop` 被否了，因为 teleop 本身就是人在远程操作，VR 也算。

还没定的：

1. **`arms_teleop` 要不要拆**。它里面是两个互相没有共用代码的独立节点：`joystick_teleop` 和 `keyboard_teleop`，都发布 `control_input`、`/cmd_vel` 和腰部命令，只有手柄会发 `/fsm_command`。建议拆成 `joystick_teleop` 和 `keyboard_teleop`（ROS 里有先例：`teleop_twist_joy`、`teleop_twist_keyboard`）。没确认。
2. **`fa_teleop` 要不要改名和拆**。它是遥操作应用而不只是 VR：大量 Python（supervisor、units、config、events、diag、ros_probe、录制、命令行 `units_cli`、Web 后端 `console/server.py`、`init_steps`），外加 C++ 的 `xr_bridge` 和 `console_launcher`。你提的 `xr_teleop` 对 XR 桥这部分是对的，对整个包不对。建议拆成 `xr_teleop`（C++ 桥）和 `teleop_app`（Python 运行时，`teleop_runtime` 也行）。C++ 不引用 Python 运行时，运行时只是用 `ros2 run fa_teleop xr_bridge_node` 启动它。没定。`fa` 是什么缩写不清楚（猜是 fiveages）。Web 静态文件在仓库根的 `web/`，不在包里。
3. 手柄和键盘统一到 `/teleop/*` 接口（设计 B）也没定。

## 3. `dual_arm` 仿真里偶发的关节速度离群

重构的回归仿真里，`dual_arm` 模式 OCS2 阶段 `left_joint4` 的峰值速度，历史上 19 次都在 0.005 到 0.014 rad/s，有两次连续出现 0.109 和 0.194，之后重跑回到 0.009，代码没有改动。

**原因没查实**。怀疑过宿主机上有别的进程抢 CPU，但我用来统计的 `pgrep -f` 会匹配到自己的命令行，采样数据无效，负载本身（0.55 到 1.05）也不高。能确定的只有：同样的代码，两次异常、一次正常，之前 19 次都正常，所以是偶发的环境或时序问题。值得在真机上留意 OCS2 阶段的峰值速度。

## 6. 真机日志与故障分级

目标：真机出异常时能靠日志定位，覆盖 xr 到机器人的整条链路，开销小；故障分“停机类”和“监控类”；有 normal 和 debug 两种模式。**已完成（仿真里）**：统一到 rclcpp 日志接口、故障码注册表（[`故障码.md`](故障码.md)）、normal/debug 模式、链路每一环的健康行和飞行记录环、出错后一条命令收集和分析（`start.sh diag`），说明见 [`日志.md`](日志.md)。**没做**：日志总大小上限、长期健康趋势；**都没在真机上验证**（见下表和“真机验证清单”）。

故障码盘点时发现的缺口，**现在都只是记录，没有改任何停机行为**，要逐条确认才会改：

| 事项 | 现状 |
|---|---|
| **日志总大小上限没有做** | 现在只有“每个单元保留最新 20 份运行日志”和 `events.log` 滚动，诊断包没有上限，debug 日志量大（约每分钟 20 MB 量级）。想做的话：配置 `log.max_total_gb`，在 `up` 和做诊断包时检查一次，超了从最旧的删（保护每个单元现在的日志、`events.log`、最新几个诊断包）；一次超长运行在两次检查之间仍可能超限 |
| PC Service 的输出已接入 `logs/pc_service/`，真机上还没确认 | `runService.sh` 会自己后台化再退出，后台化之后的 PC Service 是否还往这个文件写，要在真机上看；它自己有没有日志文件（`/opt/apps/roboticsservice/`、家目录）也要看，有的话诊断包里要加上 |
| 没有统一处理策略的情况 | 控制周期连续超时、关节状态过期、CAN 持续发送失败或反馈缺失：现在只有零散的日志或默认关闭的统计（Juxie 的 `stats_log_period_s`），没有“超过多少就切 HOLD”的规则 |
| 升级候选（注册表里写了，未实现） | MPC 连续失败 N 次（候选 5）、XR 在运动中断线超过 T 秒（候选 5）、控制周期持续超时、CAN 持续出错。是否升级为 S2（HOLD）、阈值取多少，需要你定，并且先“只记录”跑一段时间看真机数据 |
| 没有实时调度权限（SYS-001） | 容器里 `controller_manager` 报 `Could not enable FIFO RT scheduling policy`；真机上如果也出现，是否直接拒绝启动要你定 |

## 真机验证清单

重构全程只在仿真里验证（构建、测试、三种模式与基线对比）。下面这些仿真覆盖不到，需要在真机上确认：

- 诊断包（`start.sh diag`）：仿真里用真环验证过收集和报告，并注入了“进程被卡住 1.5 秒”和“进程被 kill -9”两种故障，报告都指向了对的地方；**没做**：XR 帧中断（仿真里没有头显），要带头显做一次；Marvin / Juxie 的硬件记录（401/402）和 PC Service 的输出，仿真里没有真硬件和 PC Service，只确认了能编译；**没有在真机上验证**：真实故障后窗口里的日志、故障码、健康行是否齐全，PC Service 的输出（还没接入日志，见下）有没有内容。

### 通信层重构（进行中，完成后补全）

- **目录**：`robot_drivers` 改名为 `robot_hardware`，设备驱动包平铺、不分子目录（一个设备可以同时用几种通信，按设备或按通信分目录都放不下），通信层单独放在 `robot_hardware/comm/`，包名没变，只是路径变了；真机电脑上更新代码后需要重新 `colcon build`（旧的 `build/`、`install/` 里这些包要清掉再编，Marvin 找 SDK 的相对路径也跟着改过）。
- **CAN（已合入，真机待验证）**：`JxHardware` 已经切到 `robot_comm::CanBus`，协议拆到 `juxie_protocol`。帧的内容、`sudo ip link` 命令的字符串、非阻塞读写和时序保持不变（有针对原代码的对照测试，限速限加速逻辑和原实现在 20 万组随机输入下逐一一致），但**真实总线上的收发只能在真机上验证**。步骤：
  1. 更新代码，清掉旧的 `build/`、`install/` 里的 `juxie_ros2_control`、`juxie_driver`（包已改名为 `juxie_hardware`） 再编译（新增依赖 `robot_comm_core`、`robot_comm_can`）。默认配置行为不变（`can0`、1M/5M、驱动自己执行 `sudo ip link`）。
  2. 在 `config/robot.local.yaml` 的 `hardware:` 下加 `body_can_stats_period_s: 10`，启动整机，腰、头使能后做一段典型动作（升降、转腰、点头），持续几分钟。
  3. 看 `ros2_control_node` 的日志里每 10 秒一行的 `Control loop stats`：`late` 和 `failed sends` 应该是 0，`feedback missing` 接近 0 %，`CAN tx/rx errors` 应该是 0；wake-up lateness 均值几十 µs、最大值远小于控制周期（W2 是 2 ms）。逐项含义见 [`juxie_hardware` 的“稳定性统计”](../src/robot_hardware/juxie_hardware/README.md#稳定性统计)。
  4. 正常停止后会再打印一次 `Control thread stopped, totals`。
  5. 想知道总线本身的负载和错误帧，可以另开终端 `candump -e can0`（`can-utils`）和 `ip -details -statistics link show can0`，看 `RX/TX errors`、`bus-off`、`restarts`。
  6. 故障路径：断开一个电机的电源或拔掉 CAN 线，确认驱动报 `Motor N … error` 或反馈缺失并发布 `/Base_HardwareError`，重新上电后能恢复（bus-off 自动恢复由 `restart-ms 100` 负责）。
  7. 换口（`body_can_interface: can1`）时，先重新运行 `./scripts/setup.sh host`。
  对比基线：换成新代码前，用旧版本（`git` 里 `ce788d1` 以前的提交）按同样的动作跑一次，旧版本没有统计日志，只能比较“动作是否一样平滑、有没有报错”。
- **串口（已合入，真机待验证）**：`modbus_hardware` 里 xhand1、freedom、kwr75 三份重复的 termios 代码换成了 `robot_comm::SerialPort`（`robot_comm_serial`），USB 低延迟设置和 Modbus RTU 通信器也走同一处。波特率策略不变：手（xhand1、freedom）遇到不支持的波特率回落 115200 并给警告，kwr75 不支持就连接失败。单元测试用 pty 覆盖了真实的 `PosixSerialPort`，但**真实的 USB 转 485 适配器、时序和丢帧只能在真机上验证**。步骤：
  1. 更新代码，清掉旧的 `build/`、`install/` 里的 `modbus_ros2_control`、`modbus_driver`（包已改名为 `modbus_hardware`） 再编译（新增依赖 `robot_comm_serial`）。
  2. 接 XHand1：激活，看反馈是否连续、开合是否和以前一样；日志里不应出现 `serial write failed`、`select failed`。
  3. 接 Freedom 手：同上；USB 转串口适配器的 `latency_timer` 应该被设成 1 ms（`cat /sys/bus/usb-serial/devices/ttyUSB0/latency_timer`；没权限时日志里有一条警告，行为和以前一样）。
  4. 接 KWR75 力传感器：`warmup` 能成功，六维力读数和以前一致，拔线后能报错并重连。
  5. 用同一个 485 口接 Modbus RTU 夹爪（`ModbusRtuCommunicator`），确认夹爪读写正常。
- **Modbus（已合入，真机待验证）**：新增 `robot_comm_modbus`，`ModbusMaster` 接口 + `LibmodbusRtuMaster`（原 `ModbusRtuCommunicator` 的代码，行为不变），`modbus_hardware` 里的夹爪和手都改成依赖接口。`LibmodbusRtuMaster` 用 pty 上的一个假 RTU 从站测过读写、无应答、超时、重连；`JodellGripper` 用 `MockModbusMaster` 测过。**真实夹爪和手的收发只能在真机上验证**，检查项就是上面串口那条的第 5 步，再加：
  - **Jodell 夹爪的速度行为变了**：原来私有的 `velocity_` 遮住了基类的 `velocity_`，每次读状态后命令速度被实测速度覆盖，速度状态接口一直是 0。现在命令速度固定用参数 `velocity`（默认 1.0），速度状态接口给实测值。真机上确认开合速度和以前一样（以前可能被设备回报的速度带着走）。
- **Marvin 工具口夹爪没有去重，是有意没做**：协议常量、换算和命令构造（`ModbusConfig`、`JodellCommandBuilder`、各种 Converter）本来就在 `gripper_hardware_common` 里共用，两边剩下的只是传输方式——Marvin 是 SDK 的异步收发（发请求后由 `tool_recv` 线程收），`modbus_hardware` 是 libmodbus 的同步收发。要把 Marvin 接到 `ModbusMaster` 得设计一套异步接口，而且只能上真机才能验证，现在做风险大于收益。EincinX 只在 Marvin 一侧有，没有重复。要做的话先在真机上量清楚 SDK 的收发时序再定。
