# 和真机部署包 `fa-deploy-ws` 的差异

对比对象：仓库根目录的 `fa-deploy-ws.tar`（真机部署包，`fiveages-sim/fa-deploy-ws` 的 `fa-w2` 分支）。它是旧目录布局：`arms_ros2_control`（实际检出 `19c503e`，2026-11-05）、`robot-descriptions-fiveages`（`de97e4f`）、`robot-descriptions-common`（`444d5cf`）。
我们这边：重构前的 `main`（`c9fa251`）用来做文件级对比，当前分支用来做运行时对比。

## 怎么比的（以及可信度）

三层，每层都看输出，不只看源码：

1. **源码**：重构前的 `main` 对部署包，按包逐文件比。判断一个差异是“我们旧了”还是“我们自己改的”：看我们的文件内容有没有出现在对应上游仓库的历史里（有 = 我们是旧版本，部署包更新）。
2. **生成物**：同参数渲染 xacro，对比 URDF 的链接、关节、限位、`ros2_control` 接口和硬件参数（W2 默认 / `real` / `mock`，灵巧手 `linkerhand_l6` / `xhand1`，M6 双臂 / `desktop`）。
3. **运行时**：容器里把部署包的控制器栈也编出来（27 个包），三种模式都用 `mock_components` 各跑一遍，对比控制器、节点、话题、服务、每个控制器实际生效的参数，以及同一个状态切换场景的结果。

没做 / 有限制：
- 部署包独有的硬件包（`arx`、`can`、`dexcap`、`dobot`、`eyou`、`eyou_canfd`、`ht`、`inex`、`unitree`、`wuji`）只列清单，没比内容（按你的决定）。
- 网格文件没比。`ocs2_ros2` 只看了提交号：部署包记录 `cd23b0c`，我们是 `ae75126`；部署包的运行时对比用的是我们已编好的 `ocs2`（版本和它的 `19c503e` 配套）。
- 部署包是 `mock_components` 仿真下的结果，真机上的行为没有验证。
- 这个包里的 `config/robot.local.yaml` 和模板内容几乎一样，不能说明这台真机实际改过什么，只能说明默认值。

背景：2026-11-11 `eb9ffab` 已经从 fa-deploy-ws 合并过一次，说明里写着“**没有合并**：`arms_target_manager` 的 VR 逻辑，以及已经分叉的 W2 描述文件”。下面“有意保留”一节的差异大多是那次的取舍。

## 二、参数和配置不同（不是 bug，需要你定用哪套）

运行时实际生效的值（同一个 `fiveages_w2`）：

|---|---|---|---|
| `arm_controller` | `update_rate` | 500 Hz | 100 Hz |

| | `movej_interpolation_type` | `none` | `doubles` |
| | `movel_trajectory_duration` | 2.0 | 6.0 |
| `body_joint_controller` | `home_duration` / `home_interpolation_type` | 1.5 / `linear` | 5.0 / `doubles` |

| | `movej_max_velocity` | 2.0（框架默认） | 1.2 |

我们的 W2 配置明显偏向仿真和快速遥操作（HOME 1.5 秒、不插值），部署包是真机的保守值（HOME 5 秒、插值）。**真机应该用哪一套，我没法判断。**

验证过的一点：把我们 W2 控制器的这些参数临时改成部署包的值（只改了容器里已安装的副本，已恢复），让 HOME 先完成后再对比，`whole_body` 全阶段在容差内一致，`split_body` 的 HOME / HOLD 终点完全一致、OCS2 阶段终点差 7e-4 rad，说明**同样的参数下两边代码行为一致，差异只来自配置**。

## 三、我们有、部署包没有（有意的，列出来备查）

- MPC 求解健康度日志（`MpcHealth`）、HOME 运动日志和 `home_speed_warn` 参数、状态切换日志里的 `fsm_command`。
- `jx_hardware.cpp` 的 CAN 配置带 `restart-ms 100`，与 `setup.sh` 的 sudoers 规则一致。
- Marvin SDK 作为子模块放在 `src/third_party`；`tool_dyn_identify_wizard.py`；`robot.entry` 取值改名；控制器、话题、消息的重构改名；`fa_teleop`、`w2_payload`、`WaistCommands` 等。

## 四、当时有意没合并的：`arms_target_manager` 的 VR 逻辑

14 个源文件部署包更新（上游 #76 body current target、#82 target relative、#88/#89 VR 每手夹爪模式、#90 case16 暂停、#91 dexcap online、#103 OCS2 头部 6D 跟踪等）。运行时可见的话题差异都出在这里：部署包多了 `/head_target`、`/head_current_pose`、`/body_current_target`、`/mode_command`、`/cmd_vel`，以及 `dual_arm` 下的腰部命令话题；我们多了 `/head_joint_controller/target_joint_position`。`teleop_command.yaml` 里 VR 参数两边也不同（我们有 `vr_control_scheme`，部署包有 `vr_follow_frame`、`reference_link`）。

## 五、验证过没有差异的

- `ros2_control` 关节和接口：W2 默认 20、`linkerhand_l6` 32、`xhand1` 44，两边的关节名、命令/状态接口、插件完全一致；`real` 下的硬件参数除上面的速度/加速度外一致。
- M6 双臂（`dual`、`desktop`）URDF 除 TCP 偏移链接外一致；**`dual_arm` 运行时场景两边在容差内完全一致**。
- 三种模式下控制器的名字、类型、状态一致；控制器的参数名集合一致（差异只来自重构改名）。
- 消息、RViz 插件、`lina_planning`、`ocs2_humanoid`、`arms_controller_common`（除我们多的日志）基本一致。

## 六、未判定

`split_body` OCS2 阶段 `right_joint4` 的峰值速度：我们（用部署包参数）对部署包差 0.47 到 0.63 rad/s，而部署包自己两次运行之间就差 0.17 到 0.20 rad/s。比它自身的波动大，但终点位置一致，我没有继续查。

处理时新发现、还没处理的：

- **多余的 ERROR 日志**：`body_joint_controller` 用 `doubles` 插值时，如果起点已经等于 HOME，框架先报 WARN “空操作，不是规划失败”，紧接着又打一条 ERROR “Failed to initialize trajectory manager in StateHome::enter()”。部署包里完全一样，不影响行为。
- `config/robot.local.yaml` 的 `robot.hand` 不认 `rg75`（`fa_teleop` 的字段校验只认 `none` / `linkerhand_l6` / `xhand1`），夹爪目前只能用启动参数 `type:=rg75`。
- 真机：RG75 的 Marvin 工具端口接线、力反馈、HOLD 的停止效果都没验证。
- 仍然没处理：第一节 #7（CAN 口和触觉等 xacro 参数）、#8（Marvin SDK 旧固件）、更多灵巧手和其他夹爪描述、`arms_target_manager` 的 VR 逻辑（第四节）。

## 八、一个对比时的陷阱（已修正）

规划用 URDF 有缓存，缓存键只看启动参数，**不包含被引用的 xacro 内容**。对比时部署包的 `whole_body` 命中了容器里 11 月 9 日遗留的缓存文件（`/tmp/ocs2_ros2/fiveages_w2/planning_urdf/…`），所以它用的是旧模型（`joint4` 上限 58°），而不是它当前 xacro 会生成的（0）。这会让改 xacro 之后的对比出现假的偏差（OCS2 阶段 `joint4` 终点差 0.069 rad）。把过期的缓存文件挪开重新生成后，两边规划上限都是 0，`whole_body` 终点位置在 2e-4 rad 内一致，峰值速度差 0.12 rad/s，和同一套配置自己两次之间的波动相当。**改了 xacro 之后，要让规划 URDF 重新生成**（我们自己的缓存键包含内容，不受影响；部署包的缓存键不包含，要清缓存）。前面几节里的 `whole_body` 与部署包的对比，当时双方用的规划模型都是 58°，结论本身没变。

## 九、目录和控制器重构之后的复测（2026-11-13）

重构（`robot_hardware` / `robot_control` / `robot_launch` 分组，单一 `RobotController` 拆成独立控制器包）之后，用当前分支（44 个包）和部署包控制器栈重跑了一遍第三层运行时对比：同一个容器、三种模式都用 `mock_components`、同一个状态切换场景（HOME → HOLD → OCS2 → HOLD → HOME），规划 URDF 缓存先清掉，两边都重新生成。

| 模式 | HOME / HOLD / 第二个 HOME 终点位置 | OCS2 / 第二个 HOLD 终点位置 | 速度峰值 | 启动日志错误（我们 / 部署包） |
|---|---|---|---|---|
| `dual_arm`（M6） | 完全一致 | 差 5.9e-5 rad | 一致 | 0 / 0 |
| `split_body`（W2） | 完全一致 | 差 6.9e-4 rad | OCS2 阶段 `right_joint4` 差 0.23 rad/s | 0 / 0 |
| `whole_body`（W2） | 完全一致 | 差 1.3e-4 rad | 第二个 HOLD 阶段 `left_joint4` 差 0.11 rad/s | 0 / 0 |

- 状态序列、每个阶段是否到达，两边一致。
- 速度峰值的差出在 OCS2 / HOLD 阶段，两边互有高低（例如 `whole_body` OCS2 阶段我们 0.125、部署包 0.028；第二个 HOLD 阶段我们 0.009、部署包 0.120），是 MPC 求解的瞬态抖动。第六节记过部署包自己两次运行就差 0.17 到 0.20 rad/s。
- 控制器实际生效的参数逐项比过，数值上没有差异。不同的只有：重构改名（插件类型、`cppad_library_subdir`）、规划 URDF / CppAD 缓存路径（我们 `~/.ros/ocs2_cache`，部署包 `/tmp/ocs2_ros2`）、我们多的参数（`home_speed_warn`、`waist_absolute_*_frame`、关节控制器上几个空默认值）、部署包独有的 `target_command_*`。`joint_state_broadcaster` 完全相同。

比较时要注意的一点：场景的 HOME 等待时间（`SETTLE`）要大于两边 5 秒的 HOME 插值，用 9 秒。用 4 秒时腰关节 `body_joint2` 还没到位就进入下一阶段，会出现 1e-3 到 3e-3 rad 的假差异，那是启动时间错位，不是数值差异。

没覆盖：真机；`arms_target_manager` 的 VR 逻辑；部署包独有的硬件包。
